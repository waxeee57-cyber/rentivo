# Rentivo — Adverzariális teljes audit, 2026-08-06

Két read-only audit-ügynök (edge functionök + RLS) + saját empirikus tesztek.
Minden állítás **mérve**, nem feltételezve. Ahol nincs mérés, [feltevés] jelöli.

---

## VERDIKT

A privát adat- és pénz-modell **bizonyítottan zárt**. A skepticizmus jogos volt:
**nem minden volt hibátlan.** Egy **valódi, HIGH** adatszivárgás (a két publikus
profil-tábla anonim oszlop-kitettsége) került elő — **azóta mérve zárva** (#1). Az
ellenőrzés közben egy második, funkcionális **HIGH** is kiderült: a webes storefront
100% MOCK-ot mutat egy oszlopnév-hiba miatt (#5, javítás kész, deploy launchkor).
Plusz néhány közepes/alacsony tétel.

## FINDINGS (súlyosság szerint)

### 🟢 #1 — HIGH — operators/hosts anonim oszlop-szivárgás — **JAVÍTVA (mérve zárva 2026-08-06)**
**Volt (mérve):** anonim hívó a publikálható kulccsal kiolvasta a `rentivo_operators`
MINDEN oszlopát (`stripe_account_id` mind a 6 sorra, email, phone, + ha kitöltött:
`legal_name/vat_number/registration_number/registered_address/kyc_*/push_token/
suspension_reason`), és a `rentivo_hosts`-ból `auth_id`-t (auth.users UUID), emailt,
`stripe_account_id`-t. Ok: az „Anyone can view active operators" / „public_read_hosts"
SELECT policy a teljes sort kiadta, és anonnak tábla-szintű SELECT grantja volt.
**Javítás (migr. `20260806012`–`015`):** publikus marketing-**nézetek**
(`rentivo_operators_public` / `rentivo_hosts_public`, csak aktív sor + biztonságos
oszlop); mindkét kliens (app `lib/api/listings.ts` + web `lib/listings.ts`) **két
lekérdezésre** állt (nincs embed), a tulajdonost id→név a nézetből tölti; **anon SELECT
visszavonva** az alap-táblákról; a `rentivo_listings` tulajdonos-kezelő policy-k
`authenticated`-re szűkítve, hogy az anon storefront-olvasás megmaradjon.
**Bizonyíték (anon kulccsal, mérve):** alap `rentivo_operators/hosts` szenzitív oszlop
→ **401**; `_public` nézet → **200**; anon `rentivo_listings` → **200 sorokkal**; a
12-csomagos e2e-háló újra **1047 állítás / 0 bukás**. Az `anon-surface` most
**kétirányban** őrzi (alap zárva ÉS nézet nyitva, §1b).
**Maradék (követve, nem launch-blokkoló):** authenticated-horizontális — egy
bejelentkezett user még olvashatja MÁS operator/host szenzitív alap-oszlopait
(`authenticated` megtartja az alap SELECT-et owner/admin/contract miatt). Follow-up:
own-row/admin RPC + `authenticated` revoke.

### 🟠 #2 — MEDIUM — `increment_webhook_failure` RPC hiányzott — **JAVÍTVA**
`operator-webhook-dispatch` minden hibás kézbesítésnél hívta, de a függvény nem
létezett (a hibát elnyelte) → `failure_count` sosem nőtt, egy halott endpoint örökké
újrapróbálódott. Létrehoztam (`20260806010`): növel + 10 hiba után auto-tiltás,
service_role-only.

### 🟠 #3 — MEDIUM/LOW — nyers hibaüzenet-szivárgás — **NYITVA (batch-javítandó)**
`create-booking` nyers Postgres-hibát ad vissza (`null value in column "guest_name"
… not-null constraint`); `create-payment-intent`, `delete-account`,
`operator-webhook-dispatch`, `drip-email` `error.message`-et echóz. Séma-belsőket
szivárogtat. Javítás: generikus üzenet a kliensnek, részletek a logba. (Edge-function
deploy kell, ezért batch-ben, nem launch-előtt kapkodva.)

### 🟠 #4 — HIGH-de-inert — `drip-email` nincs auth-kapu — **NYITVA (Resenddel együtt)**
`verify_jwt:true`-t a publikus anon-kulcs is kielégíti; nincs `INTERNAL_FUNCTION_SECRET`
ellenőrzés (ellentétben `send-email`-lel), nincs getUser, nincs idempotencia →
anon-kulccsal spam/„denial-of-wallet". **Jelenleg inert** (nincs `RESEND_API_KEY`,
így úgysem küld). Javítás a Resend-bekötéssel egy időben: internal-secret kapu +
per-operator-per-step „sent" idempotencia.

### 🟡 LOW tételek (dokumentálva)
- **damage-detector**: `model: 'claude-opus-4-7'` gyanús model-id — ha érvénytelen,
  a függvény mindig hibázik. `booking_id` param használatlan.
- **create-payment-intent**: idempotencia-kulcs replay egy törölt intent után (szűk).
- **operator-webhook-dispatch**: SSRF az operator-vezérelt `webhook.url`-en (belső
  secret mögött; nincs séma/host allowlist).
- **str_compliance_status nézet / rentivo_listings**: pontos `pickup_address` +
  `str_registration_number` anonnak olvasható (foglalás előtt).
- **properties tábla**: világ-olvasható + lógó anon INSERT/UPDATE/DELETE grantok
  (írás blokkolt policy-hiány miatt, de latens kockázat).
- **authenticated-horizontális maradék**: egy bejelentkezett user olvashatja MÁS
  operator/host szenzitív oszlopait (a #1 teljes javítása zárja).

### 🔴 #5 — HIGH (funkcionális, launch-blokkoló) — a webes storefront 100% MOCK-ot mutat — **NYITVA (javítás kész, deploy launchkor)**
**Mérve (2026-08-06):** a `rentivo.domrol.com/explore` a `lst-001..009` MOCK
listingeket mutatja (Porsche 911, Sprinter…), nem a DB valós sorait. Ok: a web
`lib/listings.ts` `LISTING_SELECT`-je `city, country` oszlopokat kér a
`rentivo_listings`-ből — **ezek nem léteznek** (a lokáció az operator/host `city/country`
mezőjén ül), így a lekérdezés **400**-at ad, és a `MOCK_WEB_LISTINGS` fallback lép be.
**Következmény:** amint egy VALÓS operator onboardol, a web **továbbra is elrejtené** a
valós listingjét és mockot mutatna (a 400 a valós sor beolvasása ELŐTT eldől). A tölcsér
teteje 100% hamis, nem foglalható inventárt mutat — konverzió-gyilkos launchkor.
**NEM a leak-fix okozta** (mérve: anon `rentivo_listings?select=*` → 200; kizárólag a
`city/country` oszlopnév hibás — pre-existing, a leak-fix előtt is így volt).
**Javítás (kész, nem deployolva):** a lokációt az operator/host `_public` nézetből
származtatni (van rajta `city/country`), a nem létező oszlopokat kivenni a select-ből
(`getListings`, `getListingById`, `getFeaturedListings`, `getListingCityCounts`).
**Deploy launchkor:** jelenleg a DB-ben KIZÁRÓLAG teszt-fixtúra van (minden operator
„E2E …" / „Test Operator"), így a mock demo MOST a helyes megjelenés. A javított query
élesítése a fixtúrák törlésével + az első valós operatorral egyszerre — különben a
live site teszt-szemetet („E2E Money Path Car") mutatna a látogatóknak.
